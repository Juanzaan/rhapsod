## Summary

Measured loudness normalization works for the first time, and the bot keeps a list of what is wrong with it (notices) that admins see in TeamSpeak, the panel and `/api/health`. A new install joins TeamSpeak without the panel and gets its first admin with `!claim`; installed hosts get a `rhapsod` command for status, checks, backups, updates and rollback. Each release now ships a Docker image for amd64 and arm64 and an unsigned Windows tray app for the panel. YouTube music videos can optionally skip their non-music intro and outro.

## Changes

### Loudness

- The loudness profiler never produced a profile before this release: ffmpeg ran with `-loglevel error`, which hides the loudnorm report, the report was read from stdout instead of stderr, and its values, printed as strings, were rejected. Every finite track played through dynamic single-pass `loudnorm`, and each prewarm repeated the 120-second measurement.
- A measured track plays through a fixed `volume` gain followed by `alimiter` at -1.5 dBFS. The gain stops where the measured true peak meets the -1.5 dB ceiling and never exceeds +12 dB, so the limiter only catches what the measurement missed: a quiet track with loud peaks plays slightly under the target instead of having its peaks squashed, and loud masters are still cut to the target. `loudnorm` with `linear=true`, used before, switched to its dynamic mode without notice when the loudness range was above 11 LU and resampled to 192 kHz and back; on a 3-minute test file the new chain used 0.3 s of CPU and 16 MB of memory instead of 9 s and 129 MB. The bot checks `ffmpeg -filters` at startup; a build without `alimiter` logs a warning and keeps the `loudnorm` linear pass.
- The profile covers the whole track instead of its first 120 seconds, so a gain sized for a quiet intro cannot clip a louder chorus. Tracks longer than 15 minutes are not measured and keep the dynamic filter. The next track is measured from the moment the current one starts, so first plays use their profile; nothing is measured while the queue is idle, to keep a second download away from a cold start. A measurement that fails (timeout, 403) is not retried for an hour.
- Each play measures the loudness it sent with ITU-R BS.1770 (integrated LUFS and true peak, before the `!volume` gain). `/api/metrics` exports `rhapsod_delivered_loudness_lufs` and `rhapsod_delivered_true_peak_dbtp`, the `Playback session` log line carries it as `delivered`, and `scripts/log-stats.mjs` summarizes both. On 60 s of noise the reading matches ffmpeg's `ebur128` within 0.1 LU and 0.2 dB. The meter keeps its blocks in a fixed histogram, so a metrics read costs the same after a minute or a week of radio.

### Playback

- A track ends on the tick that sends its last audio instead of one tick later, and its last partial frame (under 20 ms) is sent padded with silence instead of dropped. In tests, with the next track prewarmed, the silence between tracks at the player drops from about 40 ms to 20 ms, one frame. On a production host: [MEASURE AFTER DEPLOY: median and p95 of `rhapsod_inter_track_gap_seconds`]. The metric shows the full handoff, including the controller's work between tracks.
- A song whose ffmpeg process dies after playback started (an outage longer than ffmpeg's own reconnects, a 5xx on reconnect) resumes once from its position with a freshly resolved URL, the same way a stalled stream does. It used to end as an error and skip to the next track. A resumed song starts where its music stopped: the position no longer counts the silence sent while the stream starved, which skipped up to 5 seconds. The panel and `!np` show the same corrected position.
- Add `RHAPSOD_SKIP_NON_MUSIC` (default `false`): YouTube music videos start where the music starts and end where it ends, using the non-music segments (spoken intros, scenes, credits) that SponsorBlock users mark with the `music_offtopic` category. Only an intro and an outro are cut, never a segment in the middle, and a cut that would keep less than half the track or less than 30 seconds is ignored. The lookup sends a 4-character prefix of the SHA-256 of the video id, waits at most 1.5 seconds and runs in parallel with the audio URL; when it fails the track plays whole. The outro cut applies to prewarmed songs, to the first song after the queue was idle and to resumed songs.
- A song already in the queue is skipped by its error type, not by the wording of its Spanish chat message. Before, rewording "Esa canción ya está en la cola." would make a playlist, Spotify or Apple Music collection with a queued song fail as a whole. SoundCloud DRM errors are recognized the same way; yt-dlp DRM output is still matched by its text, since yt-dlp reports it only there.
- The live radio title cache drops expired entries; it kept one per station for the life of the process.

### Notices

- The bot keeps a list of what is wrong with it in `data/notices.json`: YouTube login, block or extraction failures, cookies that expire within 14 days, a failing yt-dlp daemon, a PO token provider that does not answer, no talk power, TeamSpeak reconnects, event-loop stalls, restart loops, a panel bound outside `127.0.0.1` and less than 1 GB free under the data directory. A notice opens only after its detector's threshold (for example three failed connects to the PO token provider in five minutes) and logs one line when it opens, escalates or resolves. Nothing is repaired automatically. While the daily YouTube check fails, it runs every 15 minutes instead of once a day.
- Admins list the open notices with `!avisos` and hide one until it gets worse with `!avisos ignorar <n>`. When the notice itself is not kept across restarts (talk power, YouTube login), its ignore is dropped at the first start more than a day after it was set, so the same problem coming back later reaches the admins again.
- Error and critical notices reach the admins who are online as a private message when they open and when they resolve, never the channel. Notices that open together go in one message, the same notice is not sent again within 6 hours and admins get at most 5 of these messages an hour; both limits are kept in `data/notices.json`, so a crash loop does not send a message on every start. With no admin online, the message waits for the first one who enters. Messages held back by the hourly cap or by a TeamSpeak reconnect go out on their own later, and a queued "[Resuelto]" is dropped when its notice opens again before delivery.
- A clean stop (a deploy, `rhapsod update`, the panel's restart button) does not count toward the restart-loop notice; before, four deploys or panel restarts within 15 minutes opened it as critical.
- The panel console shows the open notices in a card above the player, worst first, with severity, what happened and what to do. **Ignorar** works like `!avisos ignorar`; ignored notices stay listed, dimmed, until they resolve.
- `/api/health` reports the notice verdict as `verdict` (`ok`, `degraded`, `unhealthy`) and `openNotices`, without changing its status code, so a lasting notice cannot make `scripts/deploy.sh` roll back. `rhapsod status` prints the verdict when it is not `ok`, and `rhapsod doctor` warns on `degraded` and fails on `unhealthy`.

### Install and operations

- A new install asks for the TeamSpeak server and the bot joins it when the install ends, without the web panel. The installer prints a one-time code; `!claim <code>` in TeamSpeak makes the sender the first admin and saves the UID in `RHAPSOD_ADMIN_UIDS`, which new owners could not fill because they do not know their TeamSpeak UID. The panel setup wizard points to `!claim` and moves the admin UID field to an advanced section.
- New `rhapsod` command on installer hosts: `status` (services, player, TeamSpeak, pending `!claim` code, panel tunnel), `doctor` (one line per check with its fix), `password` (new random panel password), `restart` (waits for idle), `logs`, `version`, `backup`, `update`, `rollback` and `uninstall`. `update` installs the latest release through `scripts/deploy.sh`, so it waits for idle, backs up and rolls back when the new version does not come up healthy; `rollback` returns to the version the last update replaced. `restart` and `backup` stop and ask for `--force` when the panel does not answer instead of treating it as idle. `uninstall --purge` also removes the service user and its home after a last backup in `/var/backups/rhapsod`, but only when that user cannot log in (`nologin` or `false` shell). The host-independent part is `node dist/cli.js`, usable from Docker or a manual install.
- The installer no longer adds Cloudflare WARP unless `RHAPSOD_WITH_WARP=1` is set; a rerun keeps an existing WARP setup. When the daily YouTube check fails, `!stats` names the fix for the kind of failure: WARP for a blocked server address, cookies for a login request.
- Installer fixes: the service user is created before anything writes to its home, so the install no longer fails on a server where it did not exist yet; an empty `youtube-cookies.txt` is skipped instead of breaking YouTube until cookies were loaded; FFmpeg falls back to the BtbN static builds on GitHub (checked by SHA-256) when johnvansickle.com fails; RHEL 9 family servers (Rocky, Alma, Oracle Linux) keep their `curl-minimal`, and the installer, `deploy.sh` and `rhapsod update` switch to the service user with `runuser`, since RHEL's sudo drops `/usr/local/bin` from the path; Debian images without cron get `cron` (`cronie` on RHEL).
- A new CI workflow installs on fresh Ubuntu 22.04, 24.04 and arm64, Debian 12, Rocky Linux 9 and Oracle Linux 9 against a TeamSpeak 3 server and the TeamSpeak 6 beta server, and runs backup, update (including one to a version that crashes on start), rollback and uninstall.
- When `scripts/deploy.sh` rolls back a deploy that changed `scripts/yt-dlp-daemon.py`, it restarts `rhapsod-ytdlp-daemon` again after the rebuild. Before, the rolled-back bot talked to a daemon still running the failed version's script.
- yt-dlp daemon failures are logged and counted instead of falling back silently: the bot warns at most once a minute, the daemon writes failures to its journal, and `/api/metrics` exports `rhapsod_ytdlp_daemon_up` and `rhapsod_ytdlp_daemon_fallbacks_total`.
- `/api/health` answers 503 while reconnecting to TeamSpeak (it reported connected from a cached channel id) and adds the YouTube login and daemon state to its body.
- The log file is flushed before exiting, so the last line before a crash or restart reaches `data/logs`.

### Docker

- Releases publish `ghcr.io/juanzaan/rhapsod` for linux/amd64 and linux/arm64, tagged by version, minor, major and `latest`, and rebuilt weekly with the newest yt-dlp. The Compose file pulls it instead of building. The first start needs no `.env`: the container writes `data/.env` in the `rhapsod-data` volume, boots the setup mode and logs the panel password once. The image has a healthcheck against the panel, pins yt-dlp by build argument and the POT provider by digest.
- The image plays through Debian's ffmpeg. `ffmpeg-static` is now an optional dependency; when its download fails, the bot uses the ffmpeg on `PATH` instead of a path to a file that was never written.

### Windows app

- `tools/desktop` holds Rhapsod Dashboard, a Windows tray app for the panel. It keeps the SSH tunnel open and reconnects it, shows what is playing in the icon, opens the panel in its own browser window with a separate profile, runs a single copy and edits its settings in a window. The connection settings live in `%APPDATA%` and the panel password in the Windows Credential Manager; nothing is compiled into the executable.
- On the first connection to a server it shows the host key fingerprint and connects only after the user confirms it; a changed key stays an error. The password it copies for the panel login stays out of the Windows clipboard history and cloud sync. A 5xx from the panel shows its HTTP status instead of "Bot sin conexión a TeamSpeak".
- Each release carries `RhapsodDashboard.exe` and its SHA-256. The executable is not signed, so Windows SmartScreen warns on first run. CI builds it and runs its self-test on Windows.

### Panel

- Every page uses the same 1320px frame, so the nav no longer shifts between pages. Cards in a console row share their height and the queue scrolls inside its card; Settings and Commands show each group full width with an even grid.
- The Server page no longer rebuilds the channel tree every 2.5 seconds when nothing changed, which cut hover transitions mid-way. With the system set to reduce motion, only the background and the turntable stop.
- Player states read in Spanish (SONANDO, EN PAUSA, CARGANDO, EN ESPERA), and setting descriptions and wizard labels carry their Spanish accents.
- The panel waits one second before answering a wrong password, to slow down scripted guesses. Requests without credentials, such as the browser's first prompt, answer at once.

### Metrics and CI

- `/api/metrics` exports `rhapsod_frame_tick_lateness_seconds` and `rhapsod_clock_slips_total` (20 ms audio ticks more than a frame late), `rhapsod_inter_track_gap_seconds` and `rhapsod_command_to_first_audio_seconds`. Each `Playback session` log line carries the clock numbers as `clockTiming`, and `scripts/log-stats.mjs` reports the gap and the command-to-audio time.
- CI also runs the tests on Windows and on arm64 Linux, and every GitHub Action is pinned by commit SHA.

## Upgrade

No action is required beyond the v4.0.0 upgrade steps. To get the `rhapsod` command on an existing install, do not rerun the installer: on a live host it checks out the latest release tag instead of what is deployed, runs `npm ci` and a build under the running bot and rewrites the systemd units, and an install outside `/home/rhapsod/rhapsod` gets a second, empty one. After the deploy, write the wrapper's settings by hand as root, with the checkout, the service user and the `node` from `ExecStart=` in `systemctl cat rhapsod`:

```bash
install -d -m 0755 /etc/rhapsod
printf 'APP_DIR=%s\nAPP_USER=%s\nNODE_BIN=%s\n' /home/rhapsod/rhapsod rhapsod /usr/bin/node \
  > /etc/rhapsod/install.conf
install -m 0755 /home/rhapsod/rhapsod/scripts/rhapsod.sh /usr/local/bin/rhapsod
rhapsod doctor
```

Docker installs from the earlier Compose file move `.env` and `data/` into the new volume once; see [deployment](../deployment.md#docker-compose-linux). Installs with `RHAPSOD_ADMIN_UIDS` set never see a claim code; with it empty (admins by server group only) the bot creates one and says in the channel on each start that it has no admin, until someone claims it or the key is set. `RHAPSOD_LOUDNESS_TARGET_LUFS` keeps its meaning and default (-14). `RHAPSOD_SKIP_NON_MUSIC` is off unless set to `true`. Docker images now run Debian's ffmpeg; set `RHAPSOD_FFMPEG_PATH` to use another build. To go back, `sudo bash scripts/deploy.sh --ref v4.0.0`: the data format is unchanged and v4.0.0 ignores `notices.json` and `admin-claim-code`.
